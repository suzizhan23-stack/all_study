# 第14章 外部内存搜索

在本章中，我们一直使用第1.4节定义的w位word-RAM计算模型。该模型的一个隐含假设是，计算机拥有足够大的随机存取内存（random access memory, RAM）来存储数据结构中的所有数据。在某些情况下，这个假设并不成立。有些数据集合非常庞大，以至于没有计算机有足够的内存来存储它们。在这种情况下，应用程序必须将数据存储在某种外部存储介质（external storage medium）上，例如硬盘、固态硬盘，甚至网络文件服务器（它有自己的外部存储）。

访问外部存储中的一项数据极其缓慢。编写本书时所使用的计算机，其硬盘平均访问时间为19毫秒，固态硬盘平均访问时间为0.3毫秒。相比之下，计算机的随机存取内存平均访问时间不到0.000113毫秒。访问RAM比访问固态硬盘快2500倍以上，比访问硬盘快160000倍以上。

这些速度相当典型；从RAM中访问一个随机字节比从硬盘或固态硬盘中访问一个随机字节快数千倍。然而，访问时间并不能说明全部问题。当我们从硬盘或固态硬盘访问一个字节时，磁盘的整个**块（block）**都会被读取。该计算机所连接的每个驱动器的块大小都是4096；每次我们读取一个字节，驱动器就会给我们一个包含4096字节的块。如果我们仔细组织数据结构，这意味着每次磁盘访问都能提供4096字节对我们正在执行的任何操作有帮助的数据。

这就是**外部内存模型（external memory model）**的核心思想，如图14.1所示。在该模型中，计算机可以访问一个大型的外部内存，所有数据都驻留在其中。该内存被划分为多个内存**块（block）**，每个块包含$B$个字。计算机还有有限的内部内存，用于执行计算。在内部内存和外部内存之间传输一个块需要常数时间。内部内存中的计算是**免费的**；它们不花费任何时间。内部内存计算免费这一事实可能看起来有些奇怪，但它只是强调了外部内存比RAM慢得多。

<div align="center"><strong>图14.1：</strong>在外部内存模型中，访问外部内存中的单个项$x$需要将包含$x$的整个块读入RAM。</div>

在完整的外部内存模型中，内部内存的大小也是一个参数。然而，对于本章中描述的数据结构，拥有大小为$O(B+\log_B n)$的内部内存就足够了。也就是说，内存需要能够存储恒定数量的块和一个高度为$O(\log_B n)$的递归栈。在大多数情况下，$O(B)$这一项主导了内存需求。例如，即使取相对较小的值$B=32$，对于所有$n\le 2^{160}$，都有$B\ge \log_B n$。用十进制表示，对于任何

$$n\le 1\,461\,501\,637\,330\,902\,918\,203\,684\,832\,716\,283\,019\,655\,932\,542\,976$$

都有$B\ge \log_B n$。

## 14.1 块存储（Block Store）

外部存储的概念包含了大量可能的不同设备，每个设备都有自己的块大小，并通过自己的系统调用来访问。为了简化本章的阐述，使我们能够专注于共同的思想，我们用一个称为BlockStore的对象来封装外部存储设备。BlockStore存储一组内存块，每个块大小为$B$。每个块通过其整数索引唯一标识。BlockStore支持以下操作：

1. $\mathrm{read\_block}(i)$：返回索引为$i$的块的内容。
2. $\mathrm{write\_block}(i,b)$：将$b$的内容写入索引为$i$的块。
3. $\mathrm{place\_block}(b)$：返回一个新的索引，并将$b$的内容存储在该索引处。
4. $\mathrm{free\_block}(i)$：释放索引为$i$的块。这表示该块的内容不再使用，该块分配的外部内存可以被重用。

设想BlockStore的最简单方式是将其想象为存储一个被划分为多个块的文件在磁盘上，每个块包含$B$个字节。这样，$\mathrm{read\_block}(i)$和$\mathrm{write\_block}(i,b)$只是读取和写入该文件的第$iB$到$(i+1)B-1$个字节。此外，一个简单的BlockStore可以维护一个可用块的**空闲列表（free list）**。用$\mathrm{free\_block}(i)$释放的块会被添加到空闲列表中。这样，$\mathrm{place\_block}(b)$可以使用空闲列表中的块，如果没有可用的，则会在文件末尾追加一个新块。

## 14.2 B树（B-Trees）

在本节中，我们讨论二叉树的一种推广，称为**B树（B-tree）**，它在外部内存模型中非常高效。或者，B树可以看作是第9.1节中描述的2-4树的自然推广（2-4树是B树在$B=2$时的特例）。

对于任意整数$B\ge 2$，一棵**B树**是一棵树，其中所有叶子具有相同的深度，并且每个非根内部节点$u$至少有$B$个子节点，至多有$2B$个子节点。$u$的子节点存储在一个数组$u.\mathrm{children}$中。根节点的所需子节点数量有所放宽，它可以在2到$2B$个子节点之间。

如果一棵B树的高度为$h$，那么B树中叶子的数量$\ell$满足：

$$2B^{h-1} \le \ell \le 2(2B)^{h-1}$$

对第一个不等式取对数并整理项，得到：

$$
\begin{aligned}
h &\le \frac{\log \ell-1}{\log B} + 1 \\
  &\le \frac{\log \ell}{\log B} + 1 \\
  &= \log_B \ell + 1
\end{aligned}
$$

也就是说，B树的高度与叶子数的以$B$为底的对数成正比。

B树中的每个节点$u$存储一个键数组$u.\mathrm{keys}[0],\ldots,u.\mathrm{keys}[2B-1]$。如果$u$是一个拥有$k$个子节点的内部节点，那么$u$中存储的键数恰好为$k-1$，它们存储在$u.\mathrm{keys}[0],\ldots,u.\mathrm{keys}[k-2]$中。$u.\mathrm{keys}$中剩余的$2B-k+1$个数组条目被设置为$\mathrm{nil}$。如果$u$是一个非根叶子节点，那么$u$包含$B-1$到$2B-1$个键。B树中的键遵循类似于二叉搜索树中的顺序。对于任意存储了$k-1$个键的节点$u$：

$$u.\mathrm{keys}[0] < u.\mathrm{keys}[1] < \cdots < u.\mathrm{keys}[k-2]$$

如果$u$是内部节点，那么对于每个$i\in\{0,\ldots,k-2\}$，$u.\mathrm{keys}[i]$大于以$u.\mathrm{children}[i]$为根的子树中存储的每个键，但小于以$u.\mathrm{children}[i+1]$为根的子树中存储的每个键。非正式地：

$$u.\mathrm{children}[i] \prec u.\mathrm{keys}[i] \prec u.\mathrm{children}[i+1]$$

图14.2展示了一个$B=2$的B树示例。

<div align="center"><strong>图14.2：</strong>一棵$B=2$的B树。</div>

注意，B树节点中存储的数据大小为$O(B)$。因此，在外部内存环境中，选择B树中的$B$值使得一个节点能够放入单个外部内存块中。这样，在外部内存模型中执行B树操作所需的时间与操作访问（读取或写入）的节点数成正比。

例如，如果键是4字节整数，节点索引也是4字节，那么设置$B=256$意味着每个节点存储$(4+4)\times 2B = 8\times512=4096$字节的数据。这将是本章引言中讨论的硬盘或固态硬盘（块大小为4096字节）的$B$完美值。

BTree类实现了一棵B树，它存储一个BlockStore $bs$，用于存储BTree节点以及根节点的索引$ri$。和往常一样，使用整数$n$来跟踪数据结构中项的数量：

```python
def initialize():
    bs = BlockStore()
    ri = bs.place_block(Node())
    n = 0
```

### 14.2.1 搜索（Searching）

`find(x)`操作的实现（如图14.3所示）推广了二叉搜索树中的`find(x)`操作。对$x$的搜索从根开始，使用节点$u$中存储的键来确定搜索应在$u$的哪个子节点中继续。

<div align="center"><strong>图14.3：</strong>在B树中成功的搜索（查找值4）和不成功的搜索（查找值16.5）。阴影节点显示搜索过程中$z$值被更新的位置。</div>

更具体地说，在节点$u$处，搜索检查$x$是否存储在$u.\mathrm{keys}$中。如果是，则已找到$x$，搜索完成。否则，搜索找到最小的整数$i$，使得$u.\mathrm{keys}[i] > x$，并在以$u.\mathrm{children}[i]$为根的子树中继续搜索。如果$u.\mathrm{keys}$中没有键大于$x$，则搜索在$u$的最右子节点中继续。就像二叉搜索树一样，算法会跟踪最近遇到的、大于$x$的键$z$。如果$x$未找到，则返回$z$作为大于或等于$x$的最小值。

```python
def find(x):
    return find_recursive(x, ri)

def find_recursive(x, ui):
    u = bs.read_block(ui)
    i = find_it(u.keys, x)
    if i < 0:
        return u.keys[-(i+1)]
    if u.child[i] is not None:
        return find_recursive(x, u.child[i])
    return None
```

`find(x)`方法的核心是`find_it(a, x)`方法，它在一个以`nil`填充的排序数组`a`中搜索值`x`。该方法如图14.4所示，适用于任意数组`a`，其中`a[0],...,a[k-1]`是一个有序的键序列，而`a[k],...,a[length(a)-1]`都被设置为`nil`。如果`x`在数组中的位置`i`处，则`find_it(a, x)`返回`-i-1`。否则，它返回最小的索引`i`，使得`a[i] > x`或`a[i] == nil`。

```python
def find_it(a, x):
    lo = 0
    hi = len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] is None or x < a[mid]:
            hi = mid
        else:
            lo = mid + 1
    return lo
```

`find_it(a, x)`方法使用二分搜索（binary search），每一步将搜索空间减半，因此运行时间为$O(\log(\mathrm{length}(a)))$。在我们的设置中，$\mathrm{length}(a)=2B$，因此`find_it(a, x)`的运行时间为$O(\log B)$。

我们可以分析B树`find(x)`操作在通常的word-RAM模型（每条指令都计数）和外部内存模型（只计算访问的节点数）中的运行时间。由于B树中的每个叶子至少存储一个键，且具有$\ell$个叶子的B树的高度为$O(\log_B\ell)$，因此存储了$n$个键的B树的高度为$O(\log_B n)$。因此，在外部内存模型中，`find(x)`操作所需时间为$O(\log_B n)$。要确定word-RAM模型中的运行时间，我们必须考虑在访问每个节点时调用`find_it(a, x)`的开销，因此在word-RAM模型中`find(x)`的运行时间为：

$$O(\log_B n)\times O(\log B) = O(\log n)$$

### 14.2.2 添加（Addition）

B树与第6.2节中的BinarySearchTree数据结构的一个重要区别是，B树的节点不存储指向其父节点的指针。其原因稍后解释。缺少父指针意味着B树上的`add(x)`和`remove(x)`操作最容易通过递归实现。

与所有平衡搜索树一样，在`add(x)`操作期间需要某种形式的重平衡。在B树中，这是通过**分裂（splitting）**节点来完成的。请参考图14.5。虽然分裂发生在两个递归层级上，但最好将其理解为一个操作：该操作接收一个包含$2B$个键并拥有$2B+1$个子节点的节点$u$，创建一个新节点$w$，该节点接管$u.\mathrm{children}[B],\ldots,u.\mathrm{children}[2B]$。新节点$w$还接管$u$的最大的$B$个键，即$u.\mathrm{keys}[B],\ldots,u.\mathrm{keys}[2B-1]$。此时，$u$有$B$个子节点和$B$个键。多余的键$u.\mathrm{keys}[B-1]$被向上传递到$u$的父节点，父节点也接管$w$。

注意，分裂操作修改了三个节点：$u$、$u$的父节点和新节点$w$。这就是为什么B树的节点不维护父指针很重要的原因。如果它们维护父指针，那么被$w$接管的$B+1$个子节点都需要修改它们的父指针。这会将外部内存访问次数从3次增加到$B+4$次，使得B树对大的$B$值效率大大降低。

<div align="center"><strong>图14.5：</strong>在B树中分裂节点$u$（$B=3$）。注意键$u.\mathrm{keys}[2]=\mathrm{m}$从$u$传递到其父节点。</div>

B树中的`add(x)`方法如图14.6所示。在高层次上，该方法找到一个叶子$u$来添加值$x$。如果这导致$u$变得过满（因为它已经包含了$B-1$个键），则$u$被分裂。如果这导致$u$的父节点变得过满，则$u$的父节点也被分裂，这可能导致$u$的祖父节点变得过满，以此类推。这个过程继续，一次向上移动一层树，直到遇到一个未过满的节点，或者直到根节点被分裂。在前一种情况下，过程停止。在后一种情况下，创建一个新的根节点，其两个子节点是原始根节点被分裂后得到的节点。

<div align="center"><strong>图14.6：</strong>BTree中的`add(x)`操作。添加值21导致两个节点被分裂。</div>

`add(x)`方法的概要描述是：它从根节点走到叶子节点搜索$x$，将$x$添加到该叶子节点，然后沿路返回根节点，沿途分裂任何遇到的过满节点。有了这个高层视角，我们现在可以深入探讨如何递归实现该方法的细节。

`add(x)`的实际工作由`add_recursive(x, ui)`方法完成，它将值$x$添加到以标识符为$ui$的节点$u$为根的子树中。如果$u$是叶子节点，则$x$直接插入到$u.\mathrm{keys}$中。否则，$x$被递归地添加到$u$的适当子节点$u'$中。这个递归调用的结果通常是$\mathrm{nil}$，但也可能是一个新创建的节点$w$的引用，这是由于$u'$被分裂而产生的。在这种情况下，$u$接管$w$并获取其第一个键，完成对$u'$的分裂操作。

```python
def add_recursive(x, ui):
    u = bs.read_block(ui)
    i = find_it(u.keys, x)
    if i < 0:
        u.keys[-(i+1)] = x
        bs.write_block(ui, u)
        return None
    if u.children[i] is None:
        u.keys[i] = x
        n += 1
        bs.write_block(ui, u)
        return None
    w = add_recursive(x, u.children[i])
    if w is not None:
        u.keys[i] = w.key
        u.children[i+1] = w.child
        bs.write_block(ui, u)
        if u.size() >= 2*B:
            return u.split()
    return None
```

在值$x$被添加后（无论是添加到$u$还是$u$的后代），`add_recursive(x, ui)`方法检查$u$是否存储了太多键（超过$2B-1$）。如果是，则需要调用$u.\mathrm{split}()$方法来**分裂**$u$。调用$u.\mathrm{split}()$的结果是一个新节点，用做`add_recursive(x, ui)`的返回值。

`add_recursive(x, ui)`方法是`add(x)`方法的辅助方法，它调用`add_recursive(x, ri)`将$x$插入到B树的根节点中。如果`add_recursive(x, ri)`导致根节点分裂，则创建一个新的根节点，其子节点为旧根节点和旧根节点分裂产生的新节点。

```python
def add(x):
    w = add_recursive(x, ri)
    if w is not None:
        new_root = Node()
        new_root.children[0] = ri
        new_root.children[1] = w.child
        new_root.keys[0] = w.key
        ri = bs.place_block(new_root)
    return True
```

`add(x)`方法及其辅助方法`add_recursive(x, ui)`可以分两个阶段分析：

**向下阶段：** 在递归的向下阶段，在$x$被添加之前，它们访问一系列BTree节点并在每个节点上调用`find_it(a, x)`。与`find(x)`方法一样，这在外部内存模型中需要$O(\log_B n)$时间，在word-RAM模型中需要$O(\log n)$时间。

**向上阶段：** 在递归的向上阶段，在$x$被添加之后，这些方法执行最多$O(\log_B n)$次分裂。每次分裂只涉及三个节点，因此该阶段在外部内存模型中需要$O(\log_B n)$时间。然而，每次分裂涉及将$B$个键和子节点从一个节点移动到另一个节点，因此在word-RAM模型中，这需要$O(B\log n)$时间。

回顾一下，$B$的值可能非常大，甚至比$\log n$大得多。因此，在word-RAM模型中，向B树添加一个值可能比向平衡二叉搜索树添加一个值慢得多。稍后，在第14.2.4节中，我们将展示情况并没有那么糟糕；一次`add(x)`操作期间分裂操作的摊还次数是常数。这表明`add(x)`操作在word-RAM模型中的（摊还）运行时间为$O(B+\log n)$。

### 14.2.3 删除（Removal）

BTree中的`remove(x)`操作同样最容易通过递归方法实现。虽然`remove(x)`的递归实现将复杂性分散到多个方法中，但整个过程（如图14.7所示）相当直接。通过重新排列键，删除操作被简化为从某个叶子$u$中删除一个值$x'$的问题。删除$x'$可能导致$u$拥有少于$B-1$个键；这种情况称为**下溢（underflow）**。

<div align="center"><strong>图14.7：</strong>从B树中删除值4导致一次合并和一次借用操作。</div>

当下溢发生时，$u$要么从它的某个兄弟节点借用键，要么与兄弟节点合并。如果$u$与兄弟节点合并，那么$u$的父节点将少一个子节点和少一个键，这可能导致$u$的父节点下溢；这又通过借用或合并来纠正，但合并可能导致$u$的祖父节点下溢。这个过程一直向上回溯到根节点，直到不再有下溢，或者直到根节点的最后两个子节点合并为一个子节点。在后一种情况下，根节点被移除，其唯一子节点成为新的根节点。

接下来我们深入探讨每个步骤是如何实现的。`remove(x)`方法的第一个任务是找到应被删除的元素$x$。如果$x$在叶子节点中找到，则从该叶子节点中删除$x$。否则，如果$x$在某个内部节点$u$的$u.\mathrm{keys}[i]$处找到，则算法删除以$u.\mathrm{children}[i+1]$为根的子树中的最小值$x'$。值$x'$是B树中存储的大于$x$的最小值。然后用$x'$替换$u.\mathrm{keys}[i]$中的$x$。这个过程如图14.8所示。

<div align="center"><strong>图14.8：</strong>BTree中的`remove(x)`操作。要删除值$x=10$，我们将其替换为值$x'=11$，然后从包含它的叶子中删除11。</div>

`remove_recursive(x, ui)`方法是前述算法的递归实现：

```python
def remove_recursive(x, ui):
    u = bs.read_block(ui)
    i = find_it(u.keys, x)
    if i < 0:
        j = -(i+1)
        if u.children[j] is None:
            u.keys[j] = None
            n -= 1
            bs.write_block(ui, u)
            return u
        else:
            y = remove_smallest(u.children[j+1])
            u.keys[j] = y
            check_underflow(u, j)
            bs.write_block(ui, u)
            return None
    else:
        if u.children[i] is None:
            return None
        y = remove_recursive(x, u.children[i])
        if y is not None:
            u.keys[i] = y
        check_underflow(u, i)
        bs.write_block(ui, u)
        return None
```

注意，在递归地从$u$的第$i$个子节点中删除值$x$之后，`remove_recursive(x, ui)`需要确保该子节点仍然至少有$B-1$个键。在上述代码中，这是通过一个名为`check_underflow(x, i)`的方法完成的，它检查并纠正$u$的第$i$个子节点的下溢。设$w$为$u$的第$i$个子节点。如果$w$只有$B-2$个键，则需要修复。修复需要使用$w$的一个兄弟节点。这可以是$u$的第$i+1$个子节点或$u$的第$i-1$个子节点。我们通常使用$u$的第$i-1$个子节点，即$w$左侧的兄弟节点$v$。唯一不适用的情况是$i=0$，此时我们使用$w$右侧的兄弟节点。

```python
def check_underflow(u, i):
    if i > 0 and u.children[i-1].size() >= B:
        shift_rL(u, i-1, i)
    elif i < u.child_count() - 1 and u.children[i+1].size() >= B:
        shift_lR(u, i, i+1)
    else:
        if i > 0:
            merge(u, i-1)
        else:
            merge(u, i)
```

下面我们关注$i\neq 0$的情况，这样$u$的第$i$个子节点的任何下溢都将借助$u$的第$(i-1)$个子节点来纠正。$i=0$的情况类似，细节可以在附带的源代码中找到。

要修复节点$w$的下溢，我们需要为$w$找到更多的键（可能还有子节点）。有两种方法可以做到这一点：

**借用（Borrowing）：** 如果$w$有一个兄弟节点$v$拥有超过$B-1$个键，那么$w$可以从$v$借用一些键（可能还有子节点）。更具体地说，如果$v$存储了$\mathrm{size}(v)$个键，那么$v$和$w$总共拥有$B-2 + \mathrm{size}(w) \ge 2B-2$个键。因此，我们可以将键从$v$移到$w$，使得$v$和$w$各自至少有$B-1$个键。这个过程如图14.9所示。

<div align="center"><strong>图14.9：</strong>如果$v$有超过$B-1$个键，则$w$可以从$v$借用键。</div>

**合并（Merging）：** 如果$v$只有$B-1$个键，则我们必须采取更激烈的措施，因为$v$无法向$w$提供任何键。因此，如图14.10所示，我们**合并（merge）**$v$和$w$。合并操作是分裂操作的逆操作。它接收两个总共包含$2B-3$个键的节点，并将它们合并为一个包含$2B-2$个键的节点（额外的键来自于：当我们合并$v$和$w$时，它们的共同父节点$u$现在少了一个子节点，因此需要交出它的一个键）。

<div align="center"><strong>图14.10：</strong>在B树中合并两个兄弟节点$v$和$w$（$B=3$）。</div>

```python
def merge(u, i):
    v = u.children[i]
    w = u.children[i+1]
    v.keys[B-1] = u.keys[i]
    for j in range(B):
        v.keys[B+j] = w.keys[j]
        v.children[B+j] = w.children[j]
    u.keys[i] = None
    u.children[i+1] = None

```

总结一下，B树中的`remove(x)`方法遵循一条从根到叶子的路径，从叶子$u$中删除一个键$x'$，然后执行零次或多次涉及$u$及其祖先的合并操作，并执行最多一次借用操作。由于每个合并和借用操作只涉及修改三个节点，且这些操作只有$O(\log_B n)$次，整个过程在外部内存模型中需要$O(\log_B n)$时间。然而，同样地，每个合并和借用操作在word-RAM模型中需要$O(B)$时间，因此（目前）关于`remove(x)`在word-RAM模型中的运行时间，我们最多能说它是$O(B\log_B n)$。

### 14.2.4 B树的摊还分析（Amortized Analysis of B-Trees）

到目前为止，我们已经证明：

1. 在外部内存模型中，B树的`find(x)`、`add(x)`和`remove(x)`操作的运行时间为$O(\log_B n)$。
2. 在word-RAM模型中，`find(x)`的运行时间为$O(\log n)$，而`add(x)`和`remove(x)`的运行时间为$O(B\log n)$。

下面的引理表明，到目前为止，我们高估了B树执行合并和分裂操作的次数。

**引理14.1.** *从一个空的B树开始，执行任意$m$次`add(x)`和`remove(x)`操作，最多会导致$3m/2$次分裂、合并和借用操作。*

**证明。** 该证明已在第9.3节中针对$B=2$的特例进行了概述。可以使用信用方案（credit scheme）来证明该引理，其中：

1. 每次分裂、合并或借用操作用两个信用点支付，即每次发生这些操作时移除一个信用点；
2. 在任何`add(x)`或`remove(x)`操作期间，最多创建三个信用点。

由于最多创建$3m$个信用点，且每次分裂、合并和借用需要两个信用点，因此最多执行$3m/2$次分裂、合并和借用。这些信用点在图14.5、14.9和14.10中使用符号表示。

为了追踪这些信用点，证明维护以下**信用不变式（credit invariant）**：任何具有$B-1$个键的非根节点存储一个信用点，任何具有$2B-1$个键的节点存储三个信用点。拥有至少$B$个键且至多$2B-2$个键的节点不需要存储任何信用点。剩下要做的就是展示我们可以在每次`add(x)`和`remove(x)`操作期间维护信用不变式并满足上述性质1和2。

##### 14.2.4.0.1 添加（Adding）：

`add(x)`方法不执行任何合并或借用，因此我们只需要考虑由`add(x)`调用引起的分裂操作。

每次分裂操作发生是因为一个键被添加到一个已经包含$2B-1$个键的节点$u$中。此时，$u$被分裂为两个节点，分别为具有$B-1$和$B$个键的$u'$和$u''$。在此操作之前，$u$存储了$2B-1$个键，因此有三个信用点。其中两个信用点可用于支付分裂，另一个信用点可以给予$u'$（它有$B-1$个键）以维持信用不变式。因此，在任何分裂期间，我们都能支付分裂并维护信用不变式。

在`add(x)`操作期间对节点进行的唯一其他修改发生在所有分裂（如果有）完成之后。这个修改涉及向某个节点$u'$添加一个新键。如果在此之前，$u'$有$2B-2$个子节点，那么它现在有$2B-1$个子节点，因此必须获得三个信用点。这些是`add(x)`方法发放的唯一信用点。

##### 14.2.4.0.2 删除（Removing）：

在调用`remove(x)`期间，会发生零次或多次合并，并可能随后发生一次借用。每次合并发生是因为在调用`remove(x)`之前，两个节点$v$和$w$各自恰好有$B-1$个键，它们被合并为一个恰好有$2B-2$个键的节点。因此，每次这样的合并释放两个信用点，可用于支付合并。

在执行任何合并之后，最多发生一次借用操作，之后不再发生合并或借用。只有在从一个有$B-1$个键的叶子$v$中删除一个键时，才会发生借用操作。节点$v$因此有一个信用点，该信用点用于支付借用的开销。但这一个信用点不足以支付借用，因此我们创建一个信用点来完成支付。

此时，我们创建了一个信用点，还需要展示信用不变式可以维护。在最坏情况下，$v$的兄弟节点$w$在借用前恰好有$B$个键，因此之后$v$和$w$都有$B-1$个键。这意味着$v$和$w$在操作完成后各应存储一个信用点。因此，在这种情况下，我们额外创建两个信用点给予$v$和$w$。由于在一次`remove(x)`操作中最多发生一次借用，这意味着我们最多创建三个信用点，符合要求。

如果`remove(x)`操作不包括借用操作，那是因为它通过从某个在操作前有$B$个或更多键的节点中删除一个键来结束。在最坏情况下，该节点恰好有$B$个键，因此它现在有$B-1$个键，必须获得一个信用点，我们创建它。

无论哪种情况——删除操作以借用操作结束与否——在调用`remove(x)`期间最多需要创建三个信用点来维护信用不变式并支付发生的所有借用和合并。这就完成了引理的证明。∎

引理14.1的目的是表明，在word-RAM模型中，在一系列$m$次`add(x)`和`remove(x)`操作期间，分裂、合并和连接的开销仅为$O(Bm)$。也就是说，每次操作的摊还成本仅为$O(B)$，因此在word-RAM模型中`add(x)`和`remove(x)`的摊还成本为$O(B+\log n)$。以下两个定理对此进行了总结：

**定理14.1（外部内存B树）** *BTree实现了SSet接口。在外部内存模型中，BTree支持`add(x)`、`remove(x)`和`find(x)`操作，每次操作的时间为$O(\log_B n)$。*

**定理14.2（Word-RAM B树）** *BTree实现了SSet接口。在word-RAM模型中，忽略分裂、合并和借用的开销，BTree支持`add(x)`、`remove(x)`和`find(x)`操作，每次操作的时间为$O(\log n)$。此外，从一个空的BTree开始，任意序列的$m$次`add(x)`和`remove(x)`操作用于执行分裂、合并和借用的总时间为$O(Bm)$。*

## 14.3 讨论与练习（Discussion and Exercises）

外部内存计算模型由Aggarwal和Vitter引入[4]。它有时也被称为**I/O模型（I/O model）**或**磁盘访问模型（disk access model）**。

B树之于外部内存搜索，正如二叉搜索树之于内部内存搜索。B树由Bayer和McCreight于1970年引入[9]，不到十年后，Comer在ACM Computing Surveys上的文章标题就将它们称为无处不在的数据结构[15]。

与二叉搜索树一样，B树有许多变体，包括$B^+$树、$B^*$树和计数B树（counted B-tree）。B树确实无处不在，它们是许多文件系统（包括Apple的HFS+、Microsoft的NTFS和Linux的Ext4）、每个主要数据库系统以及云计算中使用的键值存储中的主要数据结构。Graefe最近的综述[36]提供了200多页的概述，涵盖了B树的许多现代应用、变体和优化。

B树实现了SSet接口。如果只需要USet接口，那么外部内存哈希（external memory hashing）可以作为B树的替代方案。外部内存哈希方案确实存在；例如，参见Jensen和Pagh[43]。这些方案在外部内存模型中实现USet操作的期望时间为$O(1)$。然而，由于各种原因，许多应用即使只要求USet操作，仍然使用B树。

B树如此受欢迎的一个原因是，它们的实际性能通常优于$O(\log_B n)$的运行时间界限所暗示的水平。原因在于，在外部内存环境中，$B$的值通常相当大——成百上千。这意味着B树中99%甚至99.9%的数据存储在叶子中。在具有大内存的数据库系统中，可以缓存B树的所有内部节点到RAM中，因为它们只占总数据集的1%或0.1%。当这种情况发生时，B树中的搜索包括非常快速的RAM搜索（通过内部节点），随后是一次外部内存访问来获取叶子。
