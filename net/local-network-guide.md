## 1. 前置准备

### 1.1 确认服务已启动

确保你的 Web 服务已正常运行。以常见项目为例：

```bash
# Next.js
yarn dev        # 默认 http://localhost:3000

# Vite
npm run dev      # 默认 http://localhost:5173

# Python Flask
flask run        # 默认 http://localhost:5000

# Python HTTP 内置服务器
python -m http.server 8080
```

### 1.2 获取本机局域网 IP

```bash
# Linux
ip a | grep inet

# macOS
ifconfig | grep inet

# Windows
ipconfig
```

输出中形如 `192.168.x.x`、`10.x.x.x` 或 `172.x.x.x` 的地址即为局域网 IP。

## 2. 局域网访问

### 2.1 绑定 `0.0.0.0` 监听

默认开发服务器只监听 `localhost`（127.0.0.1），需改为监听所有网络接口：

```bash
# Next.js
yarn dev --host 0.0.0.0

# Vite
npm run dev -- --host 0.0.0.0

# Create React App
HOST=0.0.0.0 npm start

# Python Flask
flask run --host=0.0.0.0

# Python HTTP 服务器（默认已监听所有接口）
python -m http.server 8080
```

启动后你会看到类似输出：

```
▲ Next.js 15.1.11
- Local:       http://localhost:3000
- Network:     http://192.168.1.100:3000    ← 这就是局域网地址
```

> **一句话**：`127.0.0.1` = 只接本机电话，`0.0.0.0` = 接所有电话。详见[第 5 章原理](#5-原理)。

### 2.2 其他设备访问

在同一局域网的其他设备浏览器中输入：

```
http://192.168.1.100:3000
```

将 `192.168.1.100` 替换为你的实际局域网 IP，`3000` 替换为实际端口。

### 2.4 WSL 特殊场景

WSL 1 和 WSL 2 网络架构不同，访问方式也有区别。

#### WSL 1

WSL 1 与 Windows **共享同一网络栈**，WSL 内的端口直接就是 Windows 的端口。在 WSL 中绑定 `0.0.0.0` 后，其他设备直接用 Windows 的局域网 IP 访问即可，与原生 Linux 无异。

#### WSL 2

WSL 2 运行在 Hyper-V 虚拟机中，有自己的虚拟网卡（`172.x.x.x`），与 Windows 之间是 **NAT 关系**。

**WSL 2 中启动服务后如何让局域网访问：**

```bash
# 1. 在 WSL 2 中绑定 0.0.0.0
# 以 Vite 为例：
npm run dev -- --host 0.0.0.0

# 2. 在 Windows PowerShell (管理员) 中添加端口转发
netsh interface portproxy add v4tov4 \
  listenaddress=0.0.0.0 listenport=3000 \
  connectaddress=172.x.x.x connectport=3000

# 3. Windows 防火墙放行该端口
New-NetFirewallRule -DisplayName "WSL Port 3000" \
  -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
```

其中 `172.x.x.x` 通过 WSL 内 `ip addr | grep eth0` 获取。

**注意：** Windows 11 22H2+ 会自动将 WSL 2 的端口镜像到 Windows `localhost`，但局域网仍需要手动添加 `netsh portproxy`。

**为什么本机能访问 `172.x.x.x`，但手机不能？**

```
你的本机 (Windows)                手机 (同一局域网)
      │                                  │
      │ 172.28.154.233                   │
      │ (同一虚拟交换机 ✅)                │
      │                                  │
      │ 192.168.1.100                    │ 192.168.1.200
      │ (物理网卡)                        │
      │                                  │
  ┌───┴──────────────┐                   │
  │  WSL 2 VM        │                   │
  │  172.28.154.233  │ ←── 手机不知道这个地址！
  │  ┌────────────┐  │     手机在 192.168.1.x 网段
  │  │ Web 服务   │  │     到不了 172.x.x.x 网段
  │  │ :5173      │  │     (原因：172.x.x.x 是 Hyper-V
  │  └────────────┘  │      虚拟NAT网络，与物理局域网隔离)
  └──────────────────┘
```

- **本机能访问** → Windows 和 WSL 2 在同一个 **Hyper-V 虚拟交换机**上（`172.x.x.x` 网段），直连可达
- **手机访问不到** → 手机在 **物理局域网**（`192.168.1.x`），数据包到不了 `172.x.x.x` 这个隔离的虚拟网络。必须经过 Windows 的 `netsh portproxy` 将 `Windows 局域网 IP:端口` 转发到 `WSL 虚拟 IP:端口`

#### 一键脚本

在 Windows PowerShell (管理员) 中运行以下脚本，自动配置 WSL 端口转发：

```powershell
$wsl_ip = (wsl -d Ubuntu ip addr show eth0 | Select-String -Pattern "inet\s+(\d+\.\d+\.\d+\.\d+)" | % { $_.Matches.Groups[1].Value })
$port = 3000
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=$port connectaddress=$wsl_ip connectport=$port
New-NetFirewallRule -DisplayName "WSL Port $port" -Direction Inbound -Protocol TCP -LocalPort $port -Action Allow
Write-Host "已转发 Windows :$port → WSL :$port"
```

### 2.5 防火墙放行（如有必要）

部分系统防火墙默认阻止外部连接：

```bash
# Linux (ufw)
sudo ufw allow 3000

# Linux (firewalld)
sudo firewall-cmd --add-port=3000/tcp --permanent
sudo firewall-cmd --reload

# Windows - 在"高级安全 Windows Defender 防火墙"中添加入站规则
```

## 3. 外网访问（内网穿透）

当需要让**不在同一局域网**的设备访问时，需使用内网穿透工具。

### 3.1 ngrok（推荐）

[ngrok](https://ngrok.com) 是最流行的内网穿透工具。

**安装：**

```bash
# Linux/macOS
npm install -g ngrok

# 或直接下载
# https://ngrok.com/download

# 注册后设置 token（免费版即可用）
ngrok config add-authtoken YOUR_TOKEN
```

**使用：**

```bash
# 将本地 3000 端口暴露到外网
ngrok http 3000
```

输出示例：

```
Session Status                online
Forwarding                    https://a1b2c3d4.ngrok.io -> http://localhost:3000
```

将 `https://a1b2c3d4.ngrok.io` 发给任何人即可访问。

**常用选项：**

```bash
# 指定域名（付费）
ngrok http --domain=myapp.ngrok.io 3000

# 启用基本认证
ngrok http 3000 --basic-auth="user:pass"
```

### 3.2 bore（轻量免费）

[bore](https://github.com/ekzhang/bore) 无需注册，完全开源。

**安装：**

```bash
# 或直接下载二进制
cargo install bore-cli
```

**使用：**

```bash
# 将本地 3000 端口暴露
bore local 3000 --to bore.pub
```

输出：

```
bore: listening on bore.pub:12345
```

访问 `http://bore.pub:12345` 即可。

### 3.3 Cloudflare Tunnel（生产级）

利用 Cloudflare 基础设施，无需暴露公网 IP。

**安装：**

```bash
# 下载 cloudflared
# https://developers.cloudflare.com/cloudflare-one/connections/connect-apps/install-and-setup/

# macOS
brew install cloudflared
```

**使用：**

```bash
# 快速隧道（无需域名）
cloudflared tunnel --url http://localhost:3000
```

输出：

```
Your quick Tunnel has been created! Visit it at:
https://random-name.trycloudflare.com
```

### 3.4 serveo（SSH 隧道）

利用 SSH 实现，无需额外安装客户端。

```bash
# 本地运行
ssh -R 80:localhost:3000 serveo.net
```

会输出 `https://xxx.serveo.net` 的公网地址。

### 工具对比

| 工具 | 注册 | 费用 | 带宽 | 稳定性 |
|------|------|------|------|--------|
| ngrok | 需注册 | 免费版有限制 | 较好 | 稳定 |
| bore | 无需 | 完全免费 | 一般 | 一般 |
| Cloudflare Tunnel | 需域名 | 隧道免费 | 优秀 | 优秀 |
| serveo | 无需 | 完全免费 | 慢 | 不稳定 |

## 4. 常见问题排查

### 4.1 局域网无法访问

1. **确认监听地址** — 检查是否绑定 `0.0.0.0`，而非 `127.0.0.1`
   ```bash
   # 查看实际监听端口
   ss -tlnp | grep 3000
   ```

2. **防火墙拦截** — 临时关闭防火墙测试
   ```bash
   sudo ufw disable   # Linux
   ```

3. **Windows 网络类型** — 确保网络设为"专用"而非"公用"

4. **手机热点隔离** — 部分手机热点默认开启 AP 隔离，需关闭

### 4.2 HTTPS 问题

部分浏览器特性（如 Service Worker、地理定位）要求 HTTPS：

- ngrok 和 Cloudflare Tunnel 自动提供 HTTPS
- 局域网内可使用 [mkcert](https://github.com/FiloSottile/mkcert) 自签名证书

### 4.3 端口被占用

```bash
# 查找占用进程
lsof -i :3000

# 改用其他端口
ngrok http 3001
```

## 5. 原理

### 5.1 `localhost` vs `0.0.0.0`

| 概念 | 本质 | 说明 |
|------|------|------|
| `localhost` (127.0.0.1) | **回环地址** (Loopback) | 数据包不经过物理网卡，只在操作系统内核层面绕一圈就回来。**仅本机可访问**。 |
| `0.0.0.0` | **通配地址** (Wildcard) | 表示"本机上所有的 IP 地址"，绑定它等于同时监听 `127.0.0.1` + `192.168.x.x` + 所有网络接口。 |

### 5.2 `bind()` 系统调用

`bind()` 是 Linux/Unix **系统调用**，用于将 socket 与一个 IP 地址 + 端口绑定，告诉内核"这个端口我已经占用了，发往这个 IP:Port 的数据包交给我处理"。

```c
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

**不同地址的绑定效果：**

```
bind(sockfd, addr, port)

addr = 127.0.0.1  →  只绑定回环接口，内核丢弃所有从物理网卡进来的数据包
addr = 0.0.0.0    →  绑定所有接口，内核接收从任何网络接口到达的数据包
```

监听 `127.0.0.1:3000` 时，另一台设备发往 `192.168.1.100:3000` 的数据包到达网卡 → 内核检查目标 IP 是 `192.168.1.100`，但 `bind` 没注册这个地址 → **内核返回 RST 拒绝连接**。

改为 `0.0.0.0` 后，内核看到 `192.168.1.100:3000` 有进程在监听 → **接受连接**，数据流经：`物理网卡 → 驱动 → 内核协议栈 → 你的 Web 服务进程`。

### 5.3 内核完整行为链路

```
用户进程调用 bind()
       │
       ▼
┌──────────────────────────────────┐
│        内核协议栈                 │
│                                  │
│  ① 验证权限                      │
│     - 端口 < 1024 需 root        │
│     - 检查端口是否已被占用        │
│                                  │
│  ② 将 socket 加入哈希表          │
│     (内核维护全局                 │
│      (IP,Port,协议) → sock       │
│      的哈希表)                   │
│                                  │
│  ③ 调用 listen() 后内核行为      │
│     ┌──────────────────────┐     │
│     │ 创建两个队列：        │     │
│     │ incomplete：收到 SYN │     │
│     │   但未完成三次握手    │     │
│     │ completed：已完成     │     │
│     │   三次握手的连接     │     │
│     └──────────────────────┘     │
│                                  │
│  ④ 数据包到达时内核查找流程      │
│     ┌──────────────────────┐     │
│     │ 网卡                 │     │
│     │   → 中断 → 驱动     │     │
│     │   → IP 层 → TCP 层  │     │
│     │   → 查哈希表         │     │
│     │   → 找到对应 socket  │     │
│     │   → 放入接收队列     │     │
│     │   → 唤醒用户进程     │     │
│     └──────────────────────┘     │
└──────────────────────────────────┘
```

### 5.4 关键内核行为

| 内核行为 | 说明 |
|---------|------|
| **端口独占** | 一个端口只能被一个 socket `bind`（除非设置 `SO_REUSEADDR`） |
| **地址匹配** | `127.0.0.1` → 只匹配回环接口来的包；`0.0.0.0` → 匹配所有接口 |
| **通配优先** | 同时有 `0.0.0.0:80` 和 `192.168.1.100:80`，发往 `192.168.1.100` 的包匹配更精确的那个 |
| **队列管理** | `listen()` 后内核维护两个 TCP 连接队列（半连接 + 全连接） |
| **accept 唤醒** | 全连接队列非空时 `accept()` 立即返回；空则阻塞进程 |

### 5.5 端口绑定限制

每个进程都可以调用 `bind()`，但受以下限制：

```
                进程A 想 bind(0.0.0.0:80)
                         │
                         ▼
  ┌─────────────────────────────────────┐
  │ ① 权限检查                          │
  │    端口 < 1024 → 需要 root /        │
  │    CAP_NET_BIND_SERVICE 能力        │
  │    端口 ≥ 1024 → 任意用户都可       │
  └─────────────────────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────┐
  │ ② 端口冲突检查                      │
  │    该端口已被其他进程 bind？         │
  │      是 → EADDRINUSE 错误           │
  │      否 → 继续                      │
  │    (SO_REUSEADDR 可绕过，但          │
  │     只能 bind 已关闭的 TIME_WAIT 端口)│
  └─────────────────────────────────────┘
                         │
                         ▼
  ┌─────────────────────────────────────┐
  │ ③ 地址冲突检查                      │
  │    已存在 0.0.0.0:80？              │
  │      是 → 不能 bind 192.168.1.100:80│
  │    已有 192.168.1.100:80？          │
  │      是 → 可以 bind 0.0.0.0:80      │
  │    (通配地址覆盖所有具体地址)        │
  └─────────────────────────────────────┘
```

**核心规则：**

1. **一个端口只能被一个进程独占**（默认情况下），后启动的进程拿到 `EADDRINUSE` 错误
2. **`0.0.0.0` 会覆盖所有具体 IP** — 进程 A 绑了 `0.0.0.0:3000`，进程 B 就不能再绑 `192.168.1.100:3000`（反过来可以）

## 6. 实战排错记录 — WSL2 + Clash 局域网访问踩坑

### 6.1 问题现象

```
WSL 2 中启动 Vite (npm run dev -- --host 0.0.0.0)
本机可通过 http://172.28.154.233:5173/ 访问
手机（同一局域网）访问 http://192.168.0.101:5173/ 失败
```

### 6.2 排错链路

```
手机无法访问 192.168.0.101:5173
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ① 检查 portproxy                   │ ← 发现 connectaddress 是 fe80::IPv6 地址
  │    netsh interface portproxy show   │    而不是 172.28.154.233
  │    修复：脚本 findstr 匹配到了     │
  │    多余行，加 /r "inet [0-9]" 解决  │
  └─────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ② 修复 portproxy 后仍不行           │
  │    netsh 显示正确：                  │
  │    0.0.0.0:5173 → 172.28.154.233   │
  │    防火墙规则已放行                  │
  └─────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ③ 发现 WSL warning                  │ ← 红灯信号
  │    "检测到 localhost 代理配置，      │
  │     但未镜像到 WSL"                 │
  │    排查：Windows 上运行了 Clash      │
  └─────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ④ 关掉 Clash 后仍不行               │ ← 关键发现
  │    直接访问 WSL 虚拟 IP 正常         │
  │    → 确认服务本身没问题              │
  │    → 问题出在 Windows 到 手机 这段   │
  └─────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ⑤ 排查 ipconfig                    │
  │    发现用户误以为本机 IP 是          │
  │    192.168.1.100                    │
  │    实际是 192.168.0.101             │
  └─────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────┐
  │ ⑥ 修正 IP 后仍不行                  │
  │    → 问题锁定：Clash 虚拟网卡       │
  │      即使退出 Clash，TUN 驱动残留    │
  │      在网卡层拦截流量                │
  └─────────────────────────────────────┘
```

### 6.3 根本原因

```
手机 → 192.168.0.101:5173
                  │
                  ▼
        ┌──────────────────────┐
        │  物理网卡收到数据包    │
        └──────────┬───────────┘
                   │
                   ▼
        ┌──────────────────────┐
        │  Clash TUN 虚拟网卡  │ ← 即使退出 Clash 界面，
        │  拦截并丢弃了数据包   │    TUN 驱动可能还在运行
        └──────────────────────┘
                   │
          (流量未到达用户进程)
```

Clash 的 **TUN 模式**在网卡层拦截所有流量，即使配置了"自动绕过 `192.168.*`"，在一些场景下（TUN + fake-ip 模式）绕过规则可能不生效。更隐蔽的是：**退出 Clash 界面后，TUN 虚拟网卡驱动可能仍未卸载**。

### 6.4 解决路径对比

| 方案 | 操作 | 优点 | 缺点 |
|------|------|------|------|
| **彻底退出 Clash** | 结束所有 Clash 进程 + 禁用 TUN 虚拟网卡 | 保持现有架构 | 每次使用 Clash 需开关 |
| **WSL 镜像模式** | 创建 `.wslconfig` 设置 `networkingMode=mirrored` | 一劳永逸，WSL 直接用物理 IP | 需 Windows 11 23H2+ |
| **Clash 配置绕过** | YAML 中加 `IP-CIDR` DIRECT 规则 | 不改变任何设置 | TUN 模式有时仍拦截 |

### 6.5 经验教训

| 教训 | 说明 |
|------|------|
| **不要信直觉 IP** | `ipconfig` 显示的才是真实局域网 IP，不能猜 `192.168.1.x` |
| **脚本解析 IP 要严谨** | `findstr "inet "` 可能匹配 IPv6 地址，要用 `findstr /r "inet [0-9]"` |
| **代理软件退出 ≠ 干净** | Clash TUN 驱动可能残留，需要重启或手动卸载虚拟网卡 |
| **直接访问 WSL IP 可快速定位** | 如果 `172.x.x.x:端口` 能访问而 `局域网IP:端口` 不能，问题在 Windows 网络栈而非 WSL |
| **WSL warning 是线索** | `检测到 localhost 代理配置` 提示 Windows 上有代理软件在运行 |

---

> **总结**：局域网用 `--host 0.0.0.0` + 防火墙放行；外网用 ngrok 一条命令最方便。需要 HTTPS 或长期使用推荐 Cloudflare Tunnel。WSL2 场景优先推荐镜像模式，省去 portproxy 和代理干扰的烦恼。
